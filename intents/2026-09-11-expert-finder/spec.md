# Spec — AGILEDEV-1132

## 완료 조건 (Definition of Done)

1. AGILEDEV-1132 원문의 핵심 전제 — **"정성적 평가는 배제한다. DATA 기준으로만 찾는다"** — 가 산출물
   전체(코드 + 문서)에서 재확인되어 있다. 기존 `expert_finder.py`/`experience_atoms.py`에 정성적 입력이
   섞여 있지 않음을 점검하고, 없다면 "확인 완료"로 명시한다.
2. `expert_finder.py`의 **14일(2주) 하드코딩 제한이 해제되거나 옵션화**되어 있다(예: `--since-days`
   플래그, 기본값은 이번 intent에서 담당 agent가 사용자와 논의해 결정). 최소한 "왜 이 값을 골랐는지"가
   코드 주석/문서에 남아있어야 한다.
3. **최소 2개 이상의 서로 다른 다중 기여자 저장소**로 검증되어 있다(기존 `pvs_crawler` 외 최소 1개
   추가 — 후보는 `intent.md`의 착수 전 확인 참고).
4. **"회사 안의 어떤 사람들이 전문가인지"에 명확히 답하는 최종 산출물**이 존재한다 — 모듈/기술영역별
   전문가 랭킹을 사람이 바로 읽을 수 있는 형태(CLI 출력 또는 리포트 파일)로 제공한다.
5. `developer_evaluation_metrics.md` 6.6절과 Goodhart's Law/라우팅 목적 한정 경고 문구가 이번 변경
   내용에 맞게 갱신되어 있다("전문가로 찾혔다"가 "역량이 뛰어나다"는 뜻이 아니라는 경고는 반드시
   유지).
6. `dev_metrics_code_map.md`의 코드↔문서 매핑 표에 이번에 변경/추가된 스크립트가 반영되어 있다.
7. AGILEDEV-1132에 진행 결과 요약 댓글이 남겨져 있다(`~/.claude/CLAUDE.md` 규칙에 따라 사용자 확인
   후 게시).

## 범위 밖 (Out of scope)

- **Recognition Signal / Warning Signal(개인 인정·경고 신호) 로직 변경** — 이건 AGILEDEV-1118의
  범위이며, 이 clone 티켓("전문가만 찾자")과는 목적이 다르다. 건드리지 않는다(단, `intent.md`의
  "풀어야 할 것" 4번 — 이 둘의 관계를 사용자와 먼저 정렬하는 것 자체는 이 intent의 일).
- **정성적 입력(설문, Peer Feedback, 자기 선언형 데이터) 도입** — 원문이 명시적으로 배제.
- **이메일/MS Teams/기타 MS 제품 데이터 사용** — 회사 정책상 절대 금지(AGILEDEV-1118에서 이미 확정).
- **SMILE 플랫폼 연동** — 별도 트랙, 이 프로젝트("VS")가 SMILE에 미등록 상태로 보류 중.
- **인사 평가 시스템 연동, 개인별 비교/줄세우기 UI** — 문서 7장(구 5장) "인사 평가 직접 연동 금지"
  원칙 그대로 유지.
- **타인 데이터를 이용한 개인 성과 비교·평가** — "전문가 찾기(라우팅 목적)"와 "성과 평가"를 명확히
  구분해야 하며, 후자로 전용될 수 있는 산출물(예: 기여자별 순위를 성과 지표처럼 보이게 하는 표현)은
  만들지 않는다.

## 후보 접근 (여러 안 — 최종 선택은 담당 agent가 사용자와 정렬해서 판단)

**A. 로컬 git 메타데이터만 계속 사용하되, 기간을 늘리고 다중 저장소로 확장**
- 가장 낮은 리스크·가장 빠른 구현. `expert_finder.py`의 `--since-days`를 크게 늘리거나 제거하고,
  검증 저장소를 2~3개로 늘리는 정도로 완료 조건을 만족시킬 수 있다.
- 단점: "필요한 데이터들을 최대한 모아서"라는 원문 표현을 완전히 충족하지 못할 수 있음(Gerrit/Jira
  미포함).

**B. git + Gerrit(`gerrit_metrics.py`) + Jira(`jira_metrics.py`) 결합**
- "전문가"의 정의를 코드 기여(EA)뿐 아니라 리뷰 활동(Gerrit), 이슈 처리 이력(Jira)까지 결합해
  다각화한다.
- 장점: 원문의 "필요한 데이터들을 최대한 모아서"에 가장 충실. 단점: Gerrit/Jira 실 API 인증이 필요
  (이미 `secure_info.py`/`.env`로 확보돼 있어 재사용 가능하지만, 여러 시스템을 엮는 만큼 복잡도가
  올라감).

**C. "Expert Finder"를 독립 산출물로 재정리**
- `developer_evaluation_metrics.md`가 이미 매우 방대해졌으므로(6장 이상, 여러 소항목), 이 좁은
  목적("전문가만 찾기")에는 오히려 복잡할 수 있다. 이 기능만을 위한 경량 문서(`expert_finder.md` 등)와
  스크립트 세트로 분리하는 방안.
- 장점: 사용자가 "이것만 하자"고 명시적으로 범위를 좁힌 취지에 부합. 단점: 기존 6.6절과 내용이
  중복되거나, 어느 문서가 정본인지 혼란을 줄 수 있어 마이그레이션 전략이 필요.

A/B/C는 상호 배타적이지 않다 — 예를 들어 A로 먼저 완료 조건을 만족시키고, B는 후속 확장으로 남겨둘
수도 있다. 담당 agent가 착수 전 사용자와 우선순위를 정렬할 것을 권장한다(plan.md 참고).
