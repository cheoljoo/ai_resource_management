# Modern Code Review: A Case Study at Google

- 저자: Caitlin Sadowski, Emma Söderberg, Luke Church, Michal Sipko, Alberto Bacchelli
- 출처/venue/연도: ICSE-SEIP 2018 (International Conference on Software Engineering, Software Engineering in Practice track)
- 링크: https://research.google/pubs/modern-code-review-a-case-study-at-google/ , https://sback.it/publications/icse2018seip.pdf , https://dl.acm.org/doi/10.1145/3183519.3183525

## 핵심 주장 요약
Google 내부의 "modern code review"(가벼운 도구 기반 코드 리뷰, Gerrit과 유사한 프로세스) 관행을 12건의 인터뷰, 44명 응답 설문, 그리고 실제 900만 건의 리뷰 로그 분석을 결합해 심층 조사한 산업 사례 연구다. 연구 목적은 Google이 왜 이런 코드 리뷰 프로세스를 채택했는지, 개발자들이 실제로 이를 어떻게 사용하고 어떤 동기로 참여하는지, 그리고 만족도와 어려움이 무엇인지를 규명하는 것이다. 이 논문은 코드 리뷰가 결함 탐지뿐 아니라 지식 전파, 코드베이스 일관성 유지, 팀 응집력 강화 등 다목적 기능을 수행한다는 것을 실증했고, "가벼운 도구 기반 코드 리뷰"가 오픈소스와 산업계 전반의 표준이 된 배경을 설명한다.

## 주요 발견/모델
- 코드 리뷰의 동기는 단순 결함 탐지를 넘어 지식 공유, 코드베이스 일관성, 팀 인지도(team awareness) 확보 등 다층적임.
- 대규모 로그 분석(900만 건)을 통해 리뷰 응답 속도, 리뷰 크기(변경 라인 수)와 리뷰 소요 시간의 관계 등 정량적 패턴을 도출.
- 개발자들은 신속한 리뷰 턴어라운드를 가장 중요한 만족 요인으로 꼽았고, 리뷰가 지연될 때 좌절감을 크게 느낌.
- 리뷰어 선정, 코멘트 스타일(스타일 지적 vs 구조적 지적)의 차이가 리뷰 경험과 결과 품질에 영향을 미침.
- 정량 로그(응답 시간, 리뷰 수)와 정성 인터뷰/설문을 병행해야 "왜 그런 패턴이 나타나는지"까지 설명 가능하다는 방법론적 시사점.

## 이 프로젝트에 적용한다면 (상세)
- **기존 지표 보완**: 3.1(코드 리뷰 기여도)은 이 논문과 데이터 소스·측정 대상이 거의 동일하다(Gerrit 기반 리뷰 응답 시간, 코멘트 수). 이 논문의 발견 — "리뷰 턴어라운드 속도가 만족도의 핵심"이라는 점 — 을 근거로, 3.1절에 "응답 속도"를 리뷰 "제공자" 관점뿐 아니라 "요청자" 관점(내가 올린 Change가 얼마나 빨리 첫 리뷰를 받았는지, 2.1의 리드타임과 연결)으로도 대칭적으로 분석하라는 보완을 추가할 수 있다.
  - 이 논문이 구분한 "스타일 지적 vs 구조적 지적"은 3.1절의 "LLM 시맨틱 분석(단순 동의 vs 구조적 제안 분류)" 계획과 정확히 일치한다 — 분류 카테고리를 이 논문 기준으로 세분화(스타일/기능성/설계/테스트 커버리지 등)하면 더 정교한 리뷰 품질 지표를 만들 수 있다는 구체적 근거로 인용 가능.
- **새로 추가할 지표**: 리뷰 "크기 대비 소요 시간" 상관 — 이 논문이 다룬 "리뷰 크기(diff 라인 수)와 리뷰 소요 시간의 관계"를 활용해, 3.1의 신규 세부 지표로 "커밋(Change)당 평균 diff 크기"를 함께 추적하고, 지나치게 큰 Change가 반복되는지(리뷰하기 어려운 크기로 쪼개지 않는 습관) 진단 지표로 추가할 수 있다. 이는 1.1(재작업률)과도 연결된다 — 큰 Change일수록 Patchset 수가 자연히 늘어나므로 정규화 근거로 활용.
- **Goodhart's Law/인사평가 오용 방지 시사점**: 이 논문은 코드 리뷰의 목적이 "결함 탐지"라는 단일 잣대가 아니라 지식 전파·팀 응집력 등 여러 목적을 동시에 수행한다는 것을 보여준다. 따라서 "리뷰 코멘트 수"나 "리뷰한 Change 개수" 같은 단일 수치로 리뷰어의 기여도를 순위 매기면, 조용히 지식 전파에 기여하는(짧지만 정확한 코멘트) 리뷰어를 과소평가할 위험이 있다. `developer_evaluation_metrics.md` 3.1절의 "보완 대안"에 "코멘트 개수보다 응답 속도와 구조적 제안 비율을 함께 보되, 순위화하지 않는다"는 원칙을 이 논문 근거로 명문화할 수 있다.
